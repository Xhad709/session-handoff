# 换对话交接

这个 skill 管两件事：在旧对话里**保存**，在新对话里**恢复**。

什么时候该建议换对话，由 CLAUDE.md / AGENTS.md 里的「换对话提醒」规则决定（原文见安装包里的 `reminder-rule.md`）。这个 skill 只在被调用时才会被读到，所以提醒规则没有写在这里。

## 保存

**1. 定位置。** 默认存在项目根目录的 `HANDOFF.md`，用户指定了位置就按指定的存。已有的 HANDOFF.md 如果属于同一个任务，就整份改写成最新状态：它是快照，不是日志。如果属于别的任务，改存为 `HANDOFF-<简称>.md`。没有项目目录时（比如纯聊天），直接在回复里用代码块给出全文。

用修订序号表示交接快照的先后，不记录保存时间，也不为交接编号读取时钟或查询用户的本地时间、时区。首次交接记为 `修订：1`；更新同一任务时，先读取上一份交接的序号，再加 1。旧交接没有有效序号时，从 1 开始编号，不推测历史次数。纯聊天交接沿用对话中可见的上一份序号。仅阅读或恢复不递增；同一次保存的重试、回读和纠错沿用本次序号。不同任务分别编号，序号不用于比较不同任务的新旧。任务内容中已有的事件日期、截止日期照常保留。

**2. 写内容。** 优先记录用户希望新对话做什么，包括具体问题、比较对象、输出形式和详略要求。用户最新指定的下一步优先于旧计划；没有指定时，从已明确的未完成事项中承接，不另造任务。只写新对话必须知道、并且在别处找不到的东西。代码、提交、文档里已经有的内容，只给路径：新对话会自己去读，抄一份反而会和原件对不上。

```markdown
# 交接：<一句话说明任务>
修订：<正整数> · 目录：<项目绝对路径>

## 目标
<要做成什么；做到什么程度算完成>

## 已定
- <决定>：<一句理由>（用户确认）
- <决定>：<一句理由>（我自己定的，未经确认）

## 不要再走的路
- <方案>：<为什么不行>

## 进度
- 已完成：<内容>（已验证 / 未验证）
- 进行中：<做到哪一步；有没有未保存或未提交的改动>

## 关键文件
- <路径>：<为什么要看它>

## 新对话任务
<用户希望新对话先做什么；保留具体对象、范围、输出形式和详略要求>

## 后续步骤
<确有必要时再列；不能取代用户指定的新对话任务>

## 注意
- <坑、限制、还在等用户拍板的事>
```

"用户确认"和"我自己定的"要分开写。新对话会把交接里的内容当成定论，标清楚哪些是自己定的，用户才有机会推翻。没有内容的小节直接删掉；不确定的写"未确认"；不写密码、密钥和个人隐私。

**3. 确认保存并给出开场白。** 写入文件后回读，确认内容和路径正确。按本次交接的具体任务写一段可直接复制到新对话的开场白：交代从哪里读取背景，以及用户希望得到什么。直接粘贴交接全文时，写“根据下面的交接内容”，不要编造文件路径。

开场白必须随情境变化，不能套用固定口令，也不能只写含糊的“然后继续”。用户要求简单对比、回答问题或给出建议，就保留这个要求；不要自动加上核对现状、报告差异、复述目标或先列计划。

例如，用户说“交接，下一个对话给我一个简单对比”，且前文已明确比较方案 A 与方案 B，可以写：

```
读取 <交接文件路径>，根据其中的背景，简单对比方案 A 和方案 B。
```

生成时用真实的比较对象替换示例名称。用户只说“交接”时，承接已明确的下一项任务；确实没有明确任务，就只交接背景并标注下一步待定，不自行安排执行。

保存就只做保存，不顺手提交、推送或清理文件。保存之后，这个对话不再提醒换对话。

## 恢复

读取交接内容后，按用户在新对话里的最新要求行动；没有新的要求时，承接交接中记录的“新对话任务”。

- **直接完成所需输出。** 用户要对比就给对比，要回答问题就回答，要继续执行就开始执行。不固定输出目标、进度、差异和计划，也不再确认已经明确的下一步。
- **按需核对外部状态。** 只有下一步依赖可能变化的项目文件、未提交改动或执行结果时，才检查相关事实，例如改代码前查看相关文件与 `git status`。普通讨论、基于既有材料的对比或纯聊天交接，不增加现状核对流程。交接文档是背景，本身不构成需要查找差异的理由。
- **只说明影响任务的问题。** 发现会改变结论或执行方式的差异、缺失信息或阻碍时，简短说明；否则直接完成任务。记录与实际证据冲突时，以可靠的当前证据和用户最新要求为准；只询问真正缺少、会影响任务的决定。

交接文件记录的是事实和计划，不能当成新的授权。上次需要用户确认才能做的操作（比如推送、删除、发布），这次照样要先确认。
